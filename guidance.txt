W-MD — PHASE 0 FOUNDATION + SELECTED ELITE-PRO FEATURE MIGRATION GUIDE
================================================================================
Generated from:
  • WMD.zip (authoritative W-MD project)
  • ELITE-PRO-V1-main/ElitePro.js + index.js (reference implementation)

PURPOSE
-------
W-MD is no longer being designed as a single large command switch. We are
scaling it into a modular, event-driven bot. Elite-Pro is a SOURCE OF FEATURE
LOGIC only. Its custom Baileys package/socket/session implementation must NOT
be copied into W-MD.

NON-NEGOTIABLE ARCHITECTURE RULES
---------------------------------
1. KEEP W-MD'S EXISTING Baileys 7.x RC CONNECTION LAYER AS-IS.
   Current target: @whiskeysockets/baileys 7.0.0-rc14.
   Phase 0 must not rewrite pairing, socket creation, reconnect logic, auth
   state, or the existing W-MD connection lifecycle.

2. KEEP SUPABASE / LOVABLE CLOUD AUTH ISOLATED.
   Do not modify auth/cloud connection code unless a feature explicitly needs
   persistent cloud data. The new local database is for bot-runtime settings,
   group settings, warnings, automation switches, etc.

3. MOVE FROM "MAIN HANDLER DOES EVERYTHING" TO EVENT-DRIVEN MODULES.
   The message passage/handler should normalize an incoming event, run the
   command parser/router when appropriate, and publish events to independent
   automation modules. Automations must not become a giant if/else chain.

4. OWNER / SUDO / ADMIN OPERATIONS ARE SECURITY-SENSITIVE.
   Permission checks belong in a central permission service, not duplicated
   casually in every command. Dangerous operations must fail closed.

5. LOCAL JSON DATABASE:
   Use a small database abstraction instead of calling fs.readFileSync /
   fs.writeFileSync throughout feature code. JSON is the storage backend, not
   the application API.

6. NO WELCOME SYSTEM.
   Elite's welcome/left watcher is intentionally excluded.

7. PHASE 6 FEATURES ARE BLOCKED UNTIL BAILEYS 7.x RC EVENT LIFECYCLE IS STABLE.
   Status/channel/group/session features can be prepared behind interfaces,
   but they should not be considered production-complete until connection,
   history, message, contact, group, status and credential events are stable.

PHASE 0 — FOUNDATION
================================================================================

A. COMMAND PARSER
-----------------
Importance:
The parser is the entry point for all command features. A scalable parser
separates syntax from business logic. Commands should receive a normalized
context instead of knowing how raw Baileys messages are shaped.

Recommended normalized context:
  {
    rawMessage,
    chatId,
    senderId,
    isGroup,
    text,
    command,
    args,
    quoted,
    mentionedJids,
    isFromMe
  }

Recommended flow:
  Baileys event
      ↓
  message normalizer
      ↓
  command parser
      ↓
  permission middleware
      ↓
  command registry/router
      ↓
  feature handler

Example parser:
  function parseCommand(text, prefix = '.') {
      const input = (text || '').trim()
      if (!input.startsWith(prefix)) return null

      const body = input.slice(prefix.length).trim()
      if (!body) return null

      const parts = body.split(/\s+/)
      return {
          command: parts.shift().toLowerCase(),
          args: parts,
          text: parts.join(' ')
      }
  }

Do not put group-management logic inside parseCommand().

B. COMMAND REGISTRY / ROUTER
----------------------------
Instead of:

  switch(command) {
      case 'kick': ...
      case 'tagall': ...
      case 'warn': ...
  }

use:

  const commands = new Map()

  commands.set('kick', kickCommand)
  commands.set('tag', tagCommand)
  commands.set('tagall', tagCommand)
  commands.set('warn', warnCommand)

  async function dispatch(ctx) {
      const handler = commands.get(ctx.command)
      if (!handler) return false
      await handler(ctx)
      return true
  }

Aliases should point to the same implementation. This prevents duplicate
logic for tag/tagall, setname/setsubject, gclink/grouplink/invite, etc.

C. PERMISSION SYSTEM
--------------------
Why it matters:
Once W-MD has group administration, moderation, automation settings and
session operations, permissions become a security boundary. If every command
implements its own check, one forgotten check can expose an admin operation.

Define roles/capabilities centrally:

  OWNER
  SUDO
  GROUP_OWNER
  GROUP_ADMIN
  BOT_ADMIN
  MEMBER
  PUBLIC

Prefer capability checks:

  permissions.require(ctx, 'group.manage')

rather than scattered boolean expressions.

Suggested capability examples:
  bot.owner
  bot.sudo
  group.manage
  group.members.add
  group.members.remove
  group.members.promote
  group.members.demote
  group.metadata.write
  group.moderation.warn
  group.moderation.antilink
  automation.configure
  session.manage
  status.manage

Fail closed:
  if the caller is not authorized, stop before any side effect.

D. OWNER / SUDO SYSTEM
----------------------
Owner and sudo lists are security-sensitive configuration.

Recommended local database record:

  {
    "owners": ["1234567890@s.whatsapp.net"],
    "sudo": []
  }

Rules:
  • Owner can configure the bot.
  • Sudo is an explicitly delegated elevated role.
  • Group admins do not automatically become bot sudo.
  • Never trust a user-supplied JID just because it looks like an owner JID.
  • Normalize/resolve JIDs before comparison.
  • Do not construct bot identity with user.id.split(':')[0] + '@s.whatsapp.net'.
  • Prefer W-MD's existing Baileys 7.x identity/JID helpers.

Elite source uses checks such as:
  if (!isCreator) return reply(mess.owner)
and:
  if (!isAdmins && !isGroupOwner && !isCreator) return reply(mess.admin)

Those checks demonstrate the intended security boundaries, but W-MD should
centralize them instead of copying the pattern into every command.

E. DATABASE ABSTRACTION
-----------------------
Why it matters:
Every selected automation and moderation feature needs persistent settings.
Direct fs calls spread storage assumptions across the entire codebase and make
future migration difficult.

Create:

  database/
    db.js
    files/
      bot.json
      owners.json
      groups.json
      automations.json
      warnings.json
      notes.json

Minimal API:

  await db.get('groups', groupId)
  await db.set('groups', groupId, value)
  await db.update('groups', groupId, patch)
  await db.delete('groups', groupId)
  await db.has('groups', groupId)

Implementation requirements:
  • create missing files automatically
  • atomic-ish write strategy (temp file + rename where practical)
  • JSON parse error handling
  • serialized writes to avoid concurrent corruption
  • defaults/schema validation
  • no secrets stored in plain JSON unless absolutely necessary
  • feature modules never call fs directly

Example:
  const group = await db.get('groups', chatId, {
      automation: {},
      moderation: {}
  })

  await db.update('groups', chatId, {
      automation: {
          autoread: true
      }
  })

The exact API can be adapted to W-MD's coding style.

F. EVENT BUS / AUTOMATION REGISTRY
----------------------------------
The critical design change is:

  messages.upsert
       ├── message normalizer
       ├── command router
       ├── auto-read
       ├── auto-typing
       ├── auto-recording
       ├── auto-react
       ├── chatbot
       ├── anti-link
       └── other independent listeners

Do NOT implement all of these inside the main passage handler.

Recommended interface:

  automationRegistry.register({
      name: 'autoread',
      events: ['message.received'],
      enabled: async (ctx) => db.get(...),
      handle: async (ctx) => ...
  })

Each automation owns:
  • configuration
  • enable/disable state
  • event subscription
  • error handling
  • rate limiting/deduplication where needed

ELITE CODE EXAMPLE — KICK
-------------------------
case 'kick': {
    if (!m.isGroup) return reply(mess.group);
    if (!isAdmins && !isGroupOwner && !isCreator) return reply(mess.admin);
    if (!isBotAdmins) return reply(mess.botAdmin);
    if (!text && !m.quoted && !m.mentionedJid.length) {
        return reply('❌ Please mention or reply to the user you want to *kick*!');
    }

    let target;

    if (m.mentionedJid[0]) {
        target = m.mentionedJid[0];
    } else if (m.quoted) {
        target = m.quoted.sender;
    } else {
        let number = text.replace(/[^0-9]/g, '');
        target = number + '@s.whatsapp.net';
    }

    const metadata = await EliteProTech.groupMetadata(m.chat);
    const participants = metadata.participants || [];

    let realJid = target;

    for (let p of participants) {
        if (
            p.id === target ||
            p.lid === target ||
            p.jid === target
        ) {
            realJid = p.jid || p.pn;
            break;
        }
    }

    if (realJid.endsWith('@lid')) {
        let found = participants.find(p => p.id === realJid);
        if (found) realJid = found.jid || found.pn;
    }

    let number = realJid.split('@')[0];

    try {
        await EliteProTech.groupParticipantsUpdate(m.chat, [realJid], 'remove');
        reply(`✅ ${number} has been removed successfully!`);
    } catch (e) {
        console.error(e);
        reply('❌ Failed to remove user. They might have left already or have privacy settings enabled.');
    }
    break;
}

Important adaptation:
Elite attempts to resolve id/lid/jid from group metadata. Keep that concept,
but centralize it as participantResolver.resolve(). Do not duplicate LID/PN
resolution in kick, promote, demote, warn, etc.

*Reason:* ${reason}. 
*Total Count:* ${count}/3`,
            mentions: [target]
        },

        await EliteProTech.groupParticipantsUpdate(
            m.chat,
            [target],
            'remove'

        fs.writeFileSync(
            './database/warnings.json',
            JSON.stringify(warnData, null, 2)
        )

        await EliteProTech.sendMessage(
            m.chat,
            {
                text:
`🚫 @${target.split('@')[0]} has been removed.

Reason: Warning limit exceeded.`,
                mentions: [target]
            }
        )
    }
}
break

Migration:
The persistent warning state belongs in database abstraction:
  groups[chatId].warnings[targetJid] = count

Do not allow a malformed target to become an arbitrary database key.

GCLINK / GROUP METADATA
-----------------------
Use Baileys group methods behind a group service:

  groupInviteCode(jid)
  groupParticipantsUpdate(jid, participants, action)

PHASE 2 — MODERATION FOUNDATION
================================================================================
Moderation features are security-sensitive because they can delete messages,
warn users, remove users or block callers.

Build a common moderation service:
  moderation.warn()
  moderation.deleteMessage()
  moderation.kick()
  moderation.block()
  moderation.clearChat()
  moderation.getWarnings()

Every moderation operation should:
  1. validate context
  2. validate permissions
  3. validate bot privileges
  4. resolve target
  5. execute action
  6. persist state
  7. log the result

Do not let antilink implement its own completely separate warning database.

W-MD'S SELECTED SCOPE
---------------------
The user's selected scope overrides the complete inventory above.

1) PHASE 1: essential group management + moderation list stated above.
2) PHASE 4: automation list stated by the user, with each automation
   independently configurable and event-driven.
3) PHASE 5: ONLY jid, lid, get, fetch, channel-id/channelid.
4) PHASE 6: status downloader/saver/view/like, group status, channel ID lookup,
   group member operations, group metadata, session management — ONLY after
   Baileys 7.x RC event lifecycle is stable.
5) "ALL MEDIA DOWNLOADER": prepare the architecture to accommodate the complete
   downloader family from Elite, but do not automatically ship every downloader
   until each dependency/API is reviewed.
6) "GROUP ADMINISTRATION ALL": include the complete group-administration family
   from the Elite inventory, subject to security and Baileys 7.x compatibility.
7) "MODERATION ALL": include the complete moderation family from the inventory,
   subject to security review.
8) "STATUS SYSTEM ALL": include the complete status family, but Phase 6
   production activation is gated on stable event lifecycle.
9) "CHATBOT MODE ON": chatbot is a first-class automation with independent
   DM/group/chat configuration.
10) User's references to sections 15 and 24 mean all features in those selected
    blueprint sections should be architecturally prepared, but implementation
    remains subject to the selected-scope rule and security review.

async function handleAutoReact(EliteProTech, mek) {
    try {
        if (!mek?.key || mek.key.fromMe || !mek.key.remoteJid) return
        if (!global.autoreact || emojis.length < 1) return

        const jid = mek.key.remoteJid
        if (jid === 'status@broadcast') return

        const chatType = jid.endsWith('@g.us') ? 'Group' : 'DM'
        const randomEmoji = emojis[Math.floor(Math.random() * emojis.length)]

        await EliteProTech.sendMessage(jid, {
            react: {
                text: randomEmoji,
                key: mek.key
            }
        })

        console.log(`✅ Auto-reacted in ${chatType} (${jid}) with ${randomEmoji}`)

    } catch (err) {
        console.error('❌ Auto-react error:', err.message)
    }
}

async function handleStatusWatcher(EliteProTech, mek) {
    try {
        if (!mek?.message || !mek?.key || mek.key.fromMe) return
        if (mek.key.remoteJid !== 'status@broadcast') return
        if (!global.autoviewstatus && !global.autolikestatus) return

        const msg = mek.message

        if (msg?.reactionMessage) return
        if (msg?.protocolMessage) return

        const msgId = mek.key.id

        if (processedStatusMessages.has(msgId)) return
        processedStatusMessages.add(msgId)

        setTimeout(() => {
            processedStatusMessages.delete(msgId)
        }, 5 * 60 * 1000)

        const participantJid = resolveStatusTarget(EliteProTech, mek)
        if (!participantJid) return

        const statusKey = {
            remoteJid: 'status@broadcast',
            id: msgId,
            fromMe: false,
            participant: participantJid
        }

        if (global.autoviewstatus) {
            await EliteProTech.readMessages([statusKey])
            console.log(`👀 Viewed status from ${participantJid}`)
        }

        if (!global.autolikestatus) return

        const emojis = [
            '❤️','💸','😇','🍂','💥','💯','🔥','💫','💎','💗',
            '🤍','🖤','👀','🙌','🙆','🚩','🥰','💐','😎','🤎',
            '✅','⚡','🧡','😁','😄','🌸','🕊️','🌷','⛅','🌟',
            '🗿','☠️','💜','💙','🌝','💚'
        ]

        const emoji = emojis[Math.floor(Math.random() * emojis.length)]

}

case 'fetch': {
   const fetch = require('node-fetch')
   const { format } = require('util')

   if (!q) return reply(`⚠️ Example: *${prefix + command} https://example.com*`)

   if (!/^https?:\/\//.test(q)) return reply('⚠️ URL must start with http:// or https://')

   try {
      let res = await fetch(q)

      // Prevent huge files (limit 100MB)
      if (res.headers.get('content-length') > 100 * 1024 * 1024) {
         return reply(`❌ File too large. Content-Length: ${res.headers.get('content-length')}`)
      }

      let contentType = res.headers.get('content-type') || ''
      let fileName = q.split('/').pop() || 'file'

      if (/audio/.test(contentType)) {
         return EliteProTech.sendMessage(
            m.chat,
            { audio: { url: q }, mimetype: contentType, fileName: fileName },
            { quoted: m }
         )
      } else if (/video/.test(contentType)) {
         return EliteProTech.sendMessage(
            m.chat,
            { video: { url: q }, mimetype: contentType, fileName: fileName },
            { quoted: m }
         )
      } else if (/image/.test(contentType)) {
         return EliteProTech.sendMessage(
            m.chat,
            { image: { url: q }, mimetype: contentType, fileName: fileName },
            { quoted: m }
         )
      } else if (/text|json/.test(contentType)) {
         let txt = await res.buffer()
         try {
            txt = format(JSON.parse(txt.toString()))
         } catch (e) {
            txt = txt.toString()
         } finally {
            return reply(txt.slice(0, 65536))
         }
      } else {
         // fallback to document if unknown type
         return EliteProTech.sendMessage(
            m.chat,
            { document: { url: q }, mimetype: contentType, fileName: fileName },
            { quoted: m }
         )
      }
   } catch (e) {
      reply(`❌ Error fetching URL:\n${e.message}`)
   }
}
break

LOVABLE IMPLEMENTATION DIRECTIVE
================================================================================

When implementing this guide:
  1. Inspect the current W-MD code first.
  2. Preserve the existing Baileys 7.x RC connection layer.
  3. Preserve Supabase/Lovable auth and cloud integration.
  4. Add Phase 0 as new modular infrastructure.
  5. Do not rewrite working W-MD features unless required to connect them to
     the new architecture.
  6. Extract feature behavior from Elite only; never import its custom
     Baileys package or session system.
  7. Put every background automation into its own event-driven module.
  8. Store configuration in local JSON through the database abstraction.
  9. Make owner/admin/elevated actions security-sensitive and centrally gated.
  10. Keep Phase 6 disabled until the Baileys 7.x RC lifecycle is proven stable.
  11. Add tests/smoke checks for parser, permissions, database, target
      resolution and automation toggles before adding large feature batches.
  12. Do not add the excluded welcome system.

FINAL DESIGN PRINCIPLE
----------------------
The goal is not "make W-MD have many commands."

The goal is:
  stable Baileys transport
       +
  clean event lifecycle
       +
  normalized message context
       +
  central security/permissions
       +
  local persistent configuration
       +
  modular command registry
       +
  independent automations
       +
  reusable group/moderation services
       +
  feature modules that can be enabled/disabled without destabilizing the bot.

Elite-Pro supplies proven feature ideas and implementation patterns.
W-MD supplies the connection/auth/cloud foundation and becomes the scalable
architecture.
